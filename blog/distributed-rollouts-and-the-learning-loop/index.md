# Distribute the rollouts, keep the learning loop coherent

Imagine a training system with a learner in one cluster and generation workers in several locations. The learner improves a model. The workers use copies of that model to attempt tasks and return the resulting sequences. A remote worker can be busy, produce a genuine result and still contribute nothing to the next update: by the time its work arrives, the learner may no longer admit data from that version.

That is a different problem from finding a faster link between GPUs. Geography changes when information becomes available, while learning changes which information remains useful. The opportunity is to separate work that can proceed independently from work that needs tight coordination. The cost is keeping those pieces part of the same experiment.

<a id="independent-generation-around-a-connected-learner"></a>

## Independent generation around a connected learner

A rollout records a policy attempting a task: generated tokens, or actions and observations in an environment, together with the information needed to evaluate and learn from that attempt. It is data produced for learning, not a guarantee that the answer is right or a transparent account of how the model thinks.

Distributing rollout generation need not mean distributing every gradient update across the same wide-area network. The learner can retain its tightly connected training cluster while remote workers generate sequences independently. The expensive coordination boundary then moves: model versions travel out; training data comes back. This complements rather than replaces the questions about [parallelism inside a cluster](https://rawthoughts.in/collections/useful-compute/making-the-cluster-useful/parallelism-moves-the-bottleneck/).

There is a concrete public example. The May 2025 INTELLECT-2 report separates trusted central policy updates from geographically distributed inference workers, with weight broadcasts and checks on returned data. Its described deployment retains central orchestration and discovery. The distribution of workers therefore does not imply that every coordinating function is decentralized. [INTELLECT-2 technical report, sections 2 and 3](https://arxiv.org/html/2505.07291v1).

This arrangement makes geography less restrictive for one part of the experiment. Generating independent attempts can move towards available compute while the learner retains the tightly coordinated update. Its usefulness depends on which exchanges must block progress and which can overlap with other work.

<a id="two-versions-can-both-be-genuine"></a>

## Two versions can both be genuine

Consider an illustrative sequence. A worker receives policy version 10 and begins a long task. While it works, the learner advances to version 12. The worker returns a sequence genuinely generated by version 10. An execution check confirms that fact. The result is authentic, but authenticity has not answered whether it belongs in a version-12 update.

| Event | Worker | Learner | Question carried forward |
| --- | --- | --- | --- |
| Dispatch | Starts with version 10 | Publishes version 10 | Which task, environment and reward definition apply? |
| Overlapping work | Continues its attempt | Advances through versions 11 and 12 | How much policy mismatch does this recipe tolerate? |
| Return | Supplies the version-10 trajectory | Receives it under version 12 | Is execution genuine, and is this trajectory admissible? |
| Update decision | Waits for its recorded disposition | Uses or rejects the returned data | Did checking and lag consume the economic advantage? |

The record makes a rejection intelligible. “Late” otherwise compresses a coordination problem, a learning constraint and possibly a payment dispute into one word.

Policy lag is more than a stale file. Different policies assign different probabilities to actions. Using data produced by one policy to update another changes the learning problem. IMPALA made this distinction explicit in 2018: actors send experience to learners, and the learner can advance while an actor is still collecting it. The paper's V-trace correction addresses that actor-critic mismatch. Another learning recipe still needs its own justified treatment of policy lag. [IMPALA paper, sections 3 and 4](https://arxiv.org/html/1802.01561v3).

The returned record needs to identify the policy, task, environment and reward definition that produced it, along with behaviour probabilities where the learning algorithm requires them. Those facts give the learner something a timestamp cannot: the relationship between the attempt it received and the update it is about to make.

An admission rule can then say what lag is supported and what happens outside it. That rule needs evidence from the selected learning recipe. A number of tolerated versions demonstrated for one model, task distribution and update rate is not a universal time allowance. Two updates can represent a small or a large change; one long rollout can span very different amounts of learning in different runs.

The INTELLECT-2 report describes delayed rollout generation and the rejection or disposal of outdated-checkpoint data. That is evidence of a managed trade-off, not unlimited tolerance for delay. [INTELLECT-2 technical report, sections 2.2 and 3.2](https://arxiv.org/html/2505.07291v1).

<a id="three-questions-about-one-returned-answer"></a>

## Three questions about one returned answer

Suppose the task is to multiply 14 by 17. The worker returns 243, while the expected answer is 238. The first check concerns execution: did the worker run the prescribed model configuration on the prescribed input? A genuine computation can produce that wrong answer.

Second, does the answer meet the task's criterion? Here an arithmetic checker can reject it. In a coding task, tests check their specified cases. In an open-ended task, the reward may be a much less direct proxy. Reward design has its own adequacy problem, just as [the judge of generated code needs the right contract](https://rawthoughts.in/blog/checking-generated-code/).

Third, is the returned record suitable for this update? A correct answer generated by a disallowed version may fail admission. Conversely, an incorrect answer may be useful learning data. Reinforcement learning can learn from unsuccessful attempts; filtering every failure away is not synonymous with improving the training set.

The learning loop needs all three distinctions. It can admit a genuine failure because that failure contains useful information, reject a correct answer because it arrived under an unsupported policy, or reject fabricated work before task evaluation begins.

TOPLOC addresses the execution question through compact representations of intermediate activations, checking consistency with the authorized model configuration. Its paper evaluates detection of changes to models, prompts and precision. That is narrower than proving an answer true, and the reported empirical coverage is not a universal guarantee against every possible adversary. [TOPLOC, ICML 2025](https://proceedings.mlr.press/v267/ong25a.html).

<a id="a-worker-can-optimize-the-wrong-thing"></a>

## A worker can optimize the wrong thing

Once contributors receive compensation, the returned data is also an economic object. A payment rule changes what it is rational to submit.

Paying only for correct answers can favor easy tasks if workers choose the tasks themselves. Paying only for long sequences can encourage useless length. Paying for every delivered file can encourage duplicates. These are possible failure modes of hypothetical rules, not claims that a particular network suffers them. They show why the incentive must be evaluated alongside task assignment, execution checking and admission.

A penalty is only as useful as the evidence that triggers it. The operator must distinguish cheating from a corrupted transfer, an unsupported configuration or work that became stale while in flight. Otherwise, a mechanism intended to improve trust can punish honest work for a coordination failure. Sampling checks also require a threat model: what is sampled, when contributors can learn the selection, and which attacks that selection can expose.

Task selection also determines where generation can run. A worker that sees a prompt has received its contents, regardless of whether its output is later checked. Public mathematical problems can have a wider permitted execution boundary than a private customer workflow or proprietary weights. Correct execution is useful evidence about the work, but supplies no confidentiality for material already disclosed to the worker.

<a id="the-economics-of-admitted-trajectories"></a>

## The economics of admitted trajectories

Asynchrony can let a worker generate while a learner trains or a new checkpoint travels. It can hide a wait from the critical path. It does not eliminate the bytes transferred, the resources used for checking or the consequences of arriving too late.

Suppose remote workers complete long independent tasks, model updates are comparatively infrequent, and the admitted lag is well tested. There may be substantial time to overlap communication with useful generation. Now change the conditions: tasks are short, checkpoints change frequently, and the learner needs tightly current data. Workers may spend much of their time downloading versions or returning sequences that cannot enter the update. The same network can be attractive for the first workload and poor for the second.

The comparison spans the complete loop: generation, weight distribution, result transport, checking, retry and duplicate handling, plus any learner idle time. A low worker-hour price can be consumed by frequent checkpoint downloads or by cheap sequences that reach the learner too late. Conversely, a long independent task may give the system enough time to overlap those exchanges and put otherwise unsuitable compute to useful work.

The first useful intermediate measure is the cost of obtaining data that the learning recipe actually admits and uses. "Useful" must include legitimate negative examples where appropriate, not just positively rewarded answers. The eventual measure is the cost and time of reaching the same independently evaluated learning target. More admitted trajectories are not automatically more learning, particularly if their diversity or reward information differs.

That puts [the network in the workload's economics](https://rawthoughts.in/collections/useful-compute/making-the-cluster-useful/the-network-is-part-of-the-model/) without requiring every communication path to be local. The opportunity lies in a deliberate asymmetry: varied resources produce independent experience, while a coherent learner decides how that experience enters the experiment. The return is measured in progress towards the learning target, after the cost of keeping both sides connected.
