Making the cluster useful

Model work, memory, communication and service behaviour determine what the hardware delivers.

A model finally fits across the devices, but the run barely advances. The memory problem was real; solving it exposed a different limit. This is what makes a cluster more interesting than a multiplication of accelerator specifications: its parts have to carry one computation together.

The division of work determines which exchanges happen inside a step. Their physical paths determine where that step waits. Saving memory by recomputing activations can add activity without adding the same amount of model progress. Each change solves a particular problem and changes what the next measurement means.

The useful comparison follows those changes through the same experiment: can it fit, advance, preserve progress and reach the intended quality? The experiment's design remains part of that question. Model size and training exposure decide what work the cluster receives. A changing learner receiving distributed trajectories adds a reason that genuinely completed work might no longer be useful. A faster cluster matters through the learning it can carry, not through a percentage detached from that purpose.
